# 板块 A 升级方案：聊天问答

**状态**：已定稿（讨论确认「基本满意」）  
**定稿日期**：2026-06-04

## 一、定位

**板块 A = 聊天输入端的「注意力工程」**，不是生搬硬套标准 RAG。

核心目标：在调用远端 LLM 之前，借助 **UKL、session 工作记忆、记忆固化与（后期）按需向量检索**，构建类似 Cursor「本地项目上下文」的 **持久用户上下文**，实现跨 session 的陪伴感与个性化，同时控制 token 成本与稳定性。

**灵魂是注意力机制**；向量、公共 RAG 等都是可插拔工具。

## 二、设计原则

| 原则 | 说明 |
| --- | --- |
| **输入端优化** | 生成质量取决于上下文组装，而非换模型 |
| **RAG 思想融合** | 外置记忆、按需召回、写入时沉淀；不强行套「检索→生成」流水线 |
| **分层注意力** | 便宜层每轮可用；昂贵层门控触发 |
| **叙事优于条目** | 长期记忆以叙事摘要为主，提升回复质感 |
| **事实按需召回** | 事实条目走向量检索，避免聊天变「催进度」 |
| **简单够用** | MySQL 扩展摘要表即可；规模上来再考虑独立向量库 |
| **分阶段落地** | A1 → A2 → A3 → A4，公共 RAG 更晚 |

## 三、注意力分层架构

```text
用户新消息
    │
    ▼
门控（规则/启发式）
    │
    ├─ Tier 1 每轮默认可用（低成本）
    │     ├─ UKL assemble(scene=chat)
    │     ├─ 当前 session 最近 K 轮（工作记忆）
    │     ├─ 当前 session 滚动叙事摘要
    │     └─ UKL 长期叙事记忆切片
    │
    ├─ Tier 2 门控触发（按需）
    │     ├─ 事实条目向量检索（用户显式回忆/核查时）
    │     └─ 公共知识 RAG（后期）
    │
    ▼
上下文打包 → 调用 LLM
    │
    ▼
异步写路径
    ├─ 原始消息入库（chat_message）
    ├─ session 摘要更新
    ├─ 叙事固化至 UKL
    └─ 高价值事实条目（可选入向量索引，A3）
```

## 四、各层职责

### Tier 1：每轮默认可用（A1 核心）

| 组件 | 来源 | 作用 |
| --- | --- | --- |
| **UKL `assemble_context(scene=chat)`** | D 的 profile snapshot + 其他切片 | 跨 session「一直懂你是谁」 |
| **工作记忆** | 当前 session 最近 K 轮 | 维持对话连贯 |
| **Session 滚动摘要** | 本 session 消息异步压缩 | session 变长时替代早期逐字历史，控 token |
| **长期叙事记忆** | UKL `slice_type=episodic_narrative`；E 的 `weekly_narrative` / `growth_pattern` | 阶段状态与情绪脉络，提升回复质感 |

**A1 不依赖向量**，已能解决：新 session 失忆、session 内 token 暴增、人格不连续。

### Tier 2：门控触发（A2/A3）

| 组件 | 触发条件 | 作用 |
| --- | --- | --- |
| **事实条目检索** | 规则/启发式判定用户在做显式回忆、核查、追溯 | 精准捞出具体事实，不做背景噪音 |
| **公共 RAG** | 后期；需外部知识时 | 学习方法、政策等 |

**门控倾向规则/启发式**（关键词、问句模式、显式时间引用等），节约成本，可解释。

**稳定性约束**：相似度阈值 + top-K 上限 + 时间衰减；避免无关历史被大量召回。

## 五、记忆形态与分工

| 形态 | 存储 | 读取方式 | 场景 |
| --- | --- | --- | --- |
| **叙事摘要** | UKL episodic 切片 + MySQL 摘要表 | Tier 1 默认可组装 | 长期陪伴感、情绪脉络、阶段状态 |
| **事实条目** | UKL 或 `memory_fact` 表 +（A3）向量索引 | Tier 2 门控检索 | 用户主动追溯具体事项 |
| **原始消息** | `chat_message` | 前端展示、审计；不默认全量进 prompt | 溯源 |
| **Profile 快照** | UKL（D 生产） | Tier 1 常驻 | 人格与偏好 |

### 写入策略（异步，不阻塞回复）

1. 原始消息入库（即时）
2. 更新 session 滚动叙事摘要
3. Salience 启发式：是否沉淀为长期叙事 / 是否抽取事实条目
4. 闲聊、低信息量消息 → 仅留 raw log，不固化

**避免聊天变「催进度」**：事实条目默认不进 Tier 1；只有用户表现出追溯意图或门控命中时才检索呈现。

## 六、存储方案（MySQL 简单扩展）

| 表/结构 | 用途 |
| --- | --- |
| `chat_message`（已有） | 原始消息 |
| `chat_session_summary`（新增概念） | 每 session 滚动叙事摘要 |
| UKL 切片表 | 跨 session 长期叙事、事实条目元数据 |
| `memory_embedding`（A3 可选） | 事实条目的向量；后期可迁独立向量库 |

当前需求少：摘要表 + UKL 叙事切片解决大部分问题；向量索引仅在 A3、且仅覆盖事实条目子集。

## 七、公共 RAG（后期）

| 阶段 | 能力 |
| --- | --- |
| **骨架期** | 简单手动导入接口（上传文档/文本 → 切块入库），供内部验证 |
| **成熟期** | 标准大型外部知识库 + 向量检索 + 与聊天门控集成 |

A 阶段聚焦用户私域注意力；公共 RAG 不阻塞 A1–A2。

## 八、分阶段路线图

| 阶段 | 能力 | 向量 | 公共 RAG |
| --- | --- | --- | --- |
| **A1** | UKL assemble + 工作记忆 K 轮 + session 滚动摘要 | 否 | 否 |
| **A2** | 写路径叙事固化 → UKL；门控骨架（规则） | 否 | 手动导入接口（可选） |
| **A3** | 事实条目向量检索；门控命中 episodic | 是（仅事实子集） | 预留 |
| **A4** | 正式公共 RAG 接入 | 是 | 是 |

## 九、与现有代码 / D 方案的关系

| 现有 | 升级后 |
| --- | --- |
| `process_message_in_background` 全量 session 历史拼接 | 改为注意力打包器 `build_chat_context()` |
| `build_ai_response(message)` | 接收组装后的 context 包，非裸消息 |
| D / UKL | Tier 1 每轮 `assemble_context(scene=chat)` |
| D 画像抽取 | 并行；A 负责 episodic 叙事，D 负责 profile traits；E `growth_pattern` 经 UKL 供 A Tier1 可选引用 |
| `event_bus` ON_CHAT_MESSAGE | 触发异步摘要更新与固化 pipeline |

## 十、风险与取舍

- **叙事摘要质量**依赖 LLM 压缩；需防摘要漂移，可保留摘要版本 + 时间戳
- **门控规则**初期可能漏检/误检；可日志化门控决策，迭代规则
- **UKL 未落地时**：A1 可先读 D 的 profile + 本地 session 摘要表，UKL 就绪后切换 assemble API
- **工程量**：A1 可控；A3 向量是明确增量，不前置

## 十一、讨论记录摘要

- 愿景：Cursor 式「本地持久上下文」，跨 session 不丢「人」与「阶段叙事」
- 共识：向量是工具不是灵魂；A1 无向量即有巨大提升
- 记忆：长期偏叙事摘要；事实条目仅门控/显式需求时向量检索
- 门控：规则/启发式，节约成本
- 存储：MySQL 简单扩展 + UKL，暂不复杂化
- 公共 RAG：后期；先暴露手动导入接口
- 本质：融合 RAG 思想，非僵硬套标准 RAG 流水线
